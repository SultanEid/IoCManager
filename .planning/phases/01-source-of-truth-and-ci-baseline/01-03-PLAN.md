# Plan 01-03: Validation gates and CI baseline

<objective>
Create the fast and full validation baseline that future phases can rely on. This plan covers GOV-03 and decisions D-05, D-06, D-07, and D-08.
</objective>

<context>
- Phase context: `.planning/phases/01-source-of-truth-and-ci-baseline/01-CONTEXT.md`
- Research: `.planning/phases/01-source-of-truth-and-ci-baseline/01-RESEARCH.md`
- Validation strategy: `.planning/phases/01-source-of-truth-and-ci-baseline/01-VALIDATION.md`
- Backend commands: `Workspace/Project/backend/README.md`
- Frontend scripts: `Workspace/Project/frontend/workbench/package.json`
- AI sidecar tests: `Workspace/Project/ai/service/pyproject.toml`
- Boundary guard from Plan 01-02: `Workspace/Project/scripts/check-repository-boundaries.ps1`
</context>

<must_haves>
<truths>
- D-05: Provide both a fast PR-oriented gate and a fuller local/CI validation path.
- D-06: The fast gate covers backend tests, frontend lint/typecheck/unit tests, AI sidecar tests, and secret scanning where available.
- D-07: The full validation path may include slower checks such as frontend E2E and broader build/test combinations.
- D-08: Backend commands must respect the existing MSBuild workaround from `Workspace/Project/backend/README.md` unless proven unnecessary.
</truths>
<acceptance>
- `Workspace/Project/docs/validation.md` documents fast and full validation commands.
- `.github/workflows/validation.yml` defines a fast validation path suitable for PRs.
- CI avoids local `.env` files and does not print secrets.
- Backend CI commands include `-p:MSBuildEnableWorkloadResolver=false` and `/m:1` where matching current backend docs.
- Validation docs include when to run slower E2E/full checks.
</acceptance>
</must_haves>

<threat_model>
<threat id="T-03-01" severity="medium">
CI or validation commands can accidentally depend on local secrets, skip active-stack checks, or omit the backend workaround, producing false confidence.
</threat>
<mitigation>
Document commands explicitly, keep CI scoped to active paths, include secret scanning, avoid `.env` reads, and preserve known backend restore/build/test flags.
</mitigation>
<verification>
Inspect the workflow and validation docs for backend workaround flags, frontend lint/typecheck/test commands, sidecar pytest, boundary guard, and secret scan.
</verification>
</threat_model>

<task id="1-03-02" type="auto">
<title>Add GitHub Actions validation workflow</title>
<files>
- `.github/workflows/validation.yml`
</files>
<action>
Create `.github/workflows/validation.yml` with a fast validation workflow that:
1. Runs on pull requests and pushes to active branches.
2. Checks out the repo.
3. Sets up .NET 8, Node.js, and Python 3.11.
4. Runs `Workspace/Project/scripts/check-repository-boundaries.ps1`.
5. Runs backend restore/build/test commands with the MSBuild workaround.
6. Runs frontend install, lint, typecheck, and unit tests from `Workspace/Project/frontend/workbench`.
7. Installs the AI sidecar package with dev dependencies and runs pytest from `Workspace/Project/ai/service`.
8. Runs a secret scan if a standard action or locally installable scanner is available; otherwise document why and keep a placeholder step that fails only if obvious secrets are found with a simple pattern scan.
9. Does not read local `.env` files or echo secret values.
</action>
<verify>
Run `Test-Path .github/workflows/validation.yml` and inspect the workflow for backend, frontend, sidecar, boundary, and secret-scan steps.
</verify>
<acceptance_criteria>
Workflow syntax is valid YAML and all command paths are repo-relative.
</acceptance_criteria>
</task>
